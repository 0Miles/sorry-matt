# Make the UI fast：先量，再改，再量

效能工作是一個迴圈：**基準值** → 瓶頸 → 一項改動 → 再量。留下來的每項改動都有前後數字。
開工先以本 skill 載入時標示的 base directory 為起點，全文讀取同層的
[`../build-the-ui-right/FRONTEND.md`](../build-the-ui-right/FRONTEND.md)。

## 1. 定目標與量法

寫下慢的是哪個頁面或哪個互動、看哪個指標，以及固定不變的量測條件：production build、
網路與 CPU 節流、視窗大小、快取狀態。量測用環境裡現成的工具：瀏覽器的 Performance API
（`PerformanceObserver` 的 `largest-contentful-paint`、`layout-shift`、`event`、`longtask`）、
專案已有的 Lighthouse 或 bundle 分析 script。

沒有專案自己的目標時用 Core Web Vitals 的良好門檻：LCP ≤ 2.5 秒、INP ≤ 200 毫秒、
CLS ≤ 0.1。

完成判準：對象、指標、目標值與量測條件都已寫下，且條件可以原樣重跑。

## 2. 量基準值

同一組條件至少量五次，記下中位數與最大最小值。這個範圍就是**雜訊**；之後的改善要大過它
才算數。

完成判準：每個指標都有中位數與範圍；量測指令或步驟已記下。

## 3. 指名瓶頸

用量到的資料指出一個瓶頸，寫成可以被推翻的假設：

- **LCP**：是哪個元素；時間花在 TTFB、資源開始載入前的延遲、載入本身，還是渲染延遲。
- **INP**：是哪個互動；時間花在輸入延遲、handler 執行，還是下一次繪製。
- **CLS**：是哪些元素在動、被什麼推動。
- **Bundle**：是哪些模組、哪條 import 鏈把它們帶進首屏。

完成判準：假設指得出量測資料裡的一筆證據，並說得出什麼結果會推翻它。

## 4. 查指引，改一項

針對這個瓶頸，依契約第 1 節呼叫 Skill tool 帶入 `modern-web-guidance` 查做法，照契約第 5 節
決定要不要 fallback。然後只做**一項**改動。

完成判準：diff 只包含針對這個瓶頸的一項改動，且對得上一份查過的指引或一筆量測證據。

## 5. 再量，決定去留

用第 1 步的同一組條件再量五次。改善大過雜訊就留下；沒有就退掉，把假設記為已推翻。
目標還沒達到就回到第 3 步找下一個瓶頸。

完成判準：每項嘗試過的改動都有前後中位數與「留下」或「退掉」的結論；退掉的改動已不在
working tree 裡。

## 6. 確認沒弄壞

呼叫 Skill tool 帶入 `actually-look-at-the-ui`，把每項留下的改動碰到的畫面交給它：延後載入、
拆分與 containment 最常換來空白、跳動或失效的互動。

完成判準：每項留下的改動碰到的畫面都有 `actually-look-at-the-ui` 的結果。

## 7. 回報

- **前後數字表**：`指標 | 基準中位數 | 現在中位數 | 雜訊範圍 | 目標`。
- **改動清單**：每項留下與退掉的改動，各附它對應的瓶頸與數字。
- **量測條件**，以及一句提醒：這些是實驗室數字，真實使用者的數字要看線上資料。

完成判準：表裡每個「現在」的數字都來自第 5 步最後一次量測；每項留下的改動都對得上表裡的
一個改善。
