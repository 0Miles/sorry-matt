# Make this shit pretty：重構既有 UI，功能行為不變

引數指定要重構的頁面、元件、路由或流程；沒有引數時請使用者指名範圍。

開工先以本 skill 載入時標示的 base directory 為起點，全文讀取同層的
[`../build-the-ui-right/FRONTEND.md`](../build-the-ui-right/FRONTEND.md)。它是**前端契約**；
下面粗體的**元件複用**、**寫死的值**、**狀態矩陣**、**無障礙底線**、**證據等級**與**給人看的清單**
由它定義。

接著照**元件複用**的前置處理 `docs/agents/ui.md`，讀不讀由前置決定；它不存在時在第 1 步之前停下：不開分支、
不產出 findings，請使用者執行 `/set-up-ui-skills`。

**硬護欄 —— 功能行為不變。** **行為基準**是這六項：路由、資料流、欄位與驗證規則、送出的
請求、事件追蹤、鍵盤操作；它們在重構前後相同。「鍵盤操作」指每個動作在重構前後由同樣的按鍵
觸發，且只觸發一次。例外只有一種：某一步把手刻近似元件或繞過元件庫的寫法換成元件庫元件或共用元件
時，目標元件自帶、原本沒有的按鍵記為「相同（元件補上 <按鍵>）」，算「相同」。原本會觸發的按鍵換完後
不再觸發、或同一按鍵觸發超過一次，仍是不相同。沒有遷移的動作維持「同樣的按鍵、只觸發一次」。
能改的是結構、層級、語意標記、樣式，以及補上缺的狀態。途中發現的功能缺陷記為 finding 交回報告，
留給另一次改動。

把手刻近似元件或繞過元件庫的寫法換成元件庫元件或 `ui.md` 的共用元件，屬於「補上缺的狀態或
語意」，不違反「功能行為不變」；**行為基準**六項仍逐項比對。遷移時只把業務邏輯搬到新元件上：
送出、請求、事件追蹤、導航。目標元件已提供的鍵盤、焦點與狀態 handler 不搬，例如手刻按鈕上
處理 Enter／Space 的按鍵 handler、自己維護的 focus 與 disabled 狀態；搬過去會讓同一個按鍵觸發
兩次，也違反**元件複用**禁止手寫元件已有行為的那一條。

## 1. 鎖定範圍與行為基準

確認 working tree 乾淨，列出範圍內的畫面與元件檔案，再記下三樣東西：

- 行為基準六項各自的現況與程式碼位置；鍵盤操作寫出每個動作由哪些按鍵觸發、各觸發幾次。
- 專案既有的測試、typecheck 與 lint 各跑一次的結果；既有的紅燈現在就界定清楚。
- 每個畫面在**狀態矩陣**各適用格子下的截圖，存進 scratchpad，作為**前**。

完成判準：範圍內每個檔案都已列出；行為基準六項都有現況紀錄；自動檢查結果與「前」的截圖
路徑都已記下。

## 2. 走整段旅程

從進入、主要動作到結果實際走一遍，再加一個真的**中斷情境**：驗證失敗、請求失敗、中途離開
或重複送出。看到的問題記成 finding，每則五欄：

`位置（畫面與 file:line）| 使用者看得到的後果 | 違反哪一條 | 證據等級 | 證據位置`

五個 lens 各掃一次：目的與層級、**狀態矩陣**的缺格、**無障礙底線**、沒有理由的裝飾、繞過元件庫。
可用 skill 清單裡有 `modern-web-guidance` 時，另外呼叫 Skill tool 帶入 `modern-web-guidance`
找出範圍內過時的平台寫法。

「繞過元件庫」對照 `ui.md` 的「元件庫」「共用元件」「Tokens」三段，抓三類：

- **手刻近似元件**：模仿元件庫元件或共用元件的自製元素。finding 寫出它模仿的元件名稱，以及
  該元件在 `ui.md` 裡的位置或套件。
- **外部覆寫**：**元件複用**客製化梯明列的禁止項 —— 從外部選擇器覆寫元件內部樣式、提高
  specificity 或 `!important`、私有 class 或私有 CSS 變數。
- **寫死的值**：照**元件複用**的**寫死的值**定義判定，不另訂判準；finding 寫出它對應的 token。
  不符合定義的字面值不記 finding。

這一類 finding 的**證據等級**：手刻近似元件與外部覆寫為實測（瀏覽器裡讀到的 DOM 與 computed
style），沒有瀏覽器時為未驗證，並附原始碼 `file:line`；寫死的值的證據等級與證據照**寫死的值**的定義。

完成判準：旅程的每一步與中斷情境都走過；每個 lens 都有 findings 或明記「沒有發現」；
每則 finding 五欄俱全。

## 3. 定案，交給使用者裁一次

呼叫 Skill tool 帶入 `figure-out-the-ui`，把 findings 交給它，取得新的介面定案。再把改寫切成
步驟：每一步都能獨立驗證、做完後畫面照常運作；順序是結構與層級先、狀態其次、工藝細節最後。

接著是全程唯一的**裁決點**：一次把 findings、介面定案與步驟清單交給使用者，請他裁定要做
哪些。判斷級的 finding 逐則標明它是品味問題，附上你的建議。「繞過元件庫」的 finding 不是判斷級，
不標成品味問題。

完成判準：每則 finding 都對應到一個步驟，或標為「不處理」並附原因；使用者已裁定範圍。

## 4. 小步改寫

目前在預設分支上時先開一條新分支。對每個步驟依序：

1. 呼叫 Skill tool 帶入 `build-the-ui-right` 完成這一步的改寫。
2. 呼叫 Skill tool 帶入 `actually-look-at-the-ui`，以第 1 步的截圖為「前」做**前後對照**。
3. 重跑自動檢查，結果與第 1 步一致才算過。
4. 留一個只含這一步的 commit。

某一步遷移到共用元件（抽出、改用或改了用途）或合併重複實作時，`ui.md` 的對應修改放進這一步
自己的 commit：`git show --name-only` 同時列出程式碼與 `docs/agents/ui.md`。途中發現、不是由
某一步造成的 `ui.md` 與原始碼不一致不改 `ui.md`，寫進第 5 步的 **`ui.md` 不一致**，也不為它單獨
commit。

某一步修過兩次仍未通過時，退掉它並記為未完成，繼續下一步。

完成判準：每個步驟都恰好是「已完成且有一個 commit」或「已退掉並寫出原因」；每個已完成的
步驟都有前後對照與一致的自動檢查結果。

## 5. 交付

- **Findings 對帳表**：一列一則，結果是已修、不處理或範圍外，各附 commit 或原因。
- **行為基準複核**：六項逐項比對前後，「鍵盤操作」一列寫出每個動作前後的按鍵與觸發次數；遷移後
  目標元件補上的按鍵在這一列逐個列出，各記為「相同（元件補上 <按鍵>）」。自動檢查結果與第 1 步並列。
- **前後對照**：每個畫面一組，寫出完整的截圖路徑。
- **`ui.md` 的狀態**：本次更新了哪幾列、各在哪個 commit，或為什麼無須更新。
- **`ui.md` 不一致**：途中發現、不是由某一步造成、沒修的每則不一致（含 `actually-look-at-the-ui`
  回報的），寫出 `ui.md` 的段與列，以及原始碼位置；沒有就寫「沒有」。
- **給人看的清單**，以及途中記下的功能缺陷。

完成判準：對帳表不重不漏地涵蓋第 2 步的每則 finding；行為基準六項都標為「相同」（「鍵盤操作」的
「相同（元件補上 <按鍵>）」算在內）；自動檢查結果與第 1 步一致；回報裡每一句「變好看了」都指向一組前後對照；`ui.md` 已與本次改動
一致，或明記無須更新；`ui.md` 不一致已逐則列出，或寫明「沒有」。
