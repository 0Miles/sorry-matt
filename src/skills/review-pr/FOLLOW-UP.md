# 複審：作者修正後的下一輪

複審沿用完整證據鏈，只調整候選來源與收尾：

- 步驟 1 另取回前一輪的 reviews、comments，以及**每則留言的回覆串**：
  `gh api /repos/<owner>/<repo>/pulls/<n>/reviews` 與
  `gh api /repos/<owner>/<repo>/pulls/<n>/comments`（回覆帶 `in_reply_to_id`，逐則歸戶）。
  前輪每則 blocking 留言都是必須裁決的候選：原問題是否已修復？修法是否引入新問題？
- **作者回覆過的留言，舉證責任在你身上。** 只有兩種處理：**接受並撤掉**，或**在同一串裡
  帶新證據反駁**。作者明說不修正的留言原樣重送，等於沒讀他的回覆。
- 步驟 2 的 finder 聚焦增量 commits 與修法周邊；「宣稱與實作」lens 仍檢查完整的
  `gh pr diff`，以捕捉修正 commits 夾帶的未宣稱變更，例如 lockfile 或順手修改的檔案。
- body 開頭固定交代**來源與規模**：incoming diff 是照留言小修，還是重寫？每則 finding
  標明屬於新程式碼、回歸、既有問題，或上輪漏審。一次改動上千行本質上是新 PR，新的
  blocking 變多是正常結果。
- 步驟 4 與步驟 8 的 body 逐項銷帳：前輪每項發現標為已修復、未修復或部分修復，並附
  驗證證據；新發現依原規則分流。
- 前輪問題全數修復且沒有新的 blocking 發現時使用 `APPROVE`；其餘情況依步驟 8 選擇 event。
  `APPROVE` 的 body 仍保留逐項驗證證據。

完成判準：前輪每項發現都有最新裁決與證據；作者回覆過的每則留言都已接受撤回或帶新證據
反駁；新增變更已完整檢查；送出的 event 與現存的 blocking 狀態一致。
