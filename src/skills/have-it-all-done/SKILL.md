# have-it-all-done：整件事交給我，完成後再通知你

引數（可選）＝任務描述，或明確指向既有 grilling 成果／文件。

一次取得實作授權，接著自主跑完規劃與實作，並把每個代答決定留下紀錄。

## 0. 自主執行

風險閘門放行（步驟 1）之後，目標是一路跑到交棒：中途只在步驟 2 的裁決點與步驟 5 的目視
驗收把使用者叫回來。六條規則全程有效：

- **可逆的內部決定自己做。** 本機檔案、本地分支的 commit、worktree、測試，以及權限設定
  放行的合併與部署，一律自己決定、依 `ASKING.md` 第 3 節記錄、繼續跑。
- **閘門的拒絕是指示。** 流程閘門或品質閘門擋下一次呼叫並附上該怎麼做時，照它說的改做法
  再試。只有改法不存在、或照做後仍被擋，才算卡住。
- **硬停項目進清單，繼續做其他的。** `ASKING.md` 第 5 節的永久例外與被權限擋下的動作
  逐項記進**人工作業清單**，然後繼續跑其他每一件做得了的事。
- **確認呼叫排到最後，背靠背跑完。** 一個呼叫本身會觸發確認視窗（hook 詢問、內建刪除
  檢查）就是**確認呼叫**；即使使用者早就說過「做完就送」也一樣排到最後，讓打斷集中在
  最後一次。
- **needs-triage 的票分兩段展開。** 凍結的是票集成員，不是票的內容深度。範圍內的票只標著
  needs-triage 時，凍結前只補到能排序的程度：一句範圍、阻塞邊，按 tracker 慣例標成
  ready-for-agent。**完整展開** —— 驗收項與實作層級的裁定 —— 延到該票進入 frontier 的
  那一刻，由 `get-to-work` 開輪時的展開 agent 在實作 agent 開工前完成；補驗收項的不是要
  通過它的人。上游實作會改寫下游的事實，提前裁定的那些就是要重做的那些。展開所需的事實查不到才標待裁決；執行期間新開的 needs-triage 票屬背景，
  留到交棒。
- **主持人的上下文有預算**，依 `ASKING.md` 第 7 節。

交給每個 subagent 的內容都要自足：它要遵守的規則都寫在交付內容裡，要讀的檔案都給絕對
路徑。它問不到使用者，交付內容裡也不能有要它問人的地方。

完成判準：風險閘門到交棒之間，只有裁決點與目視驗收兩次把使用者叫回來；每個硬停項目都在
人工作業清單上；每個確認呼叫都排在其他步驟之後且集中連續執行；範圍內每張 needs-triage
的票都已完成第一段展開，或已標待裁決並寫出查不到的那個事實。

## 1. 接棒並通過風險閘門

以本 skill 載入時標示的 base directory 為起點，讀同層的 [`ASKING.md`](ASKING.md) 全文，
依它第 0 節開場、第 7 節接手或建立 run ledger。建立或接手時，第 10 欄要有本 skill 的
`SKILL.md`、`ASKING.md` 與同層 `../get-to-work/SKILL.md` 的絕對路徑，缺的補上。`ASKING.md` 是本 skill 與
`take-this`、`get-to-work` 共用的契約，全程適用。

依以下優先序界定唯一任務：

1. 有引數：採用引數描述的任務，以及引數明確帶入的 grilling 成果或文件。
2. 無引數，但目前 session 有一份明確對應同一任務的完整 `grill-me`、`grill-with-docs` 或
   `grill-them` 成果：直接接棒該任務、決策與文件。
3. 以上皆無：呼叫 Skill tool 帶入 `issue-chain`，不帶引數；納入鏈上可執行的環，
   needs-triage 的票依第 0 節自行展開後一併納入，其餘**待裁決**項目留待最終報告。

任務界定後，只開一次風險閘門。逐項判定：

- **變更範圍過大**：跨多個模組、大規模重構、資料遷移、部署或安全邊界。
- **需求過於模糊**：仍有會改變實作方向的分岔、缺少可驗證的完成判準，或無法確認該承接
  哪份 grilling 成果。
- **驗收依據薄弱**：任務又大又模糊且缺少測試防護網，或成果主要仰賴 UI／文案等主觀判斷。

已有 grilling 成果時，以其中的決策與證據判定。出現紅燈時照報三燈，提案依 `ASKING.md`
第 2 節 (a) 從「全開」起跳，逐項列出紅燈的具體理由與證據。替代路徑列為備選而非推薦：
請使用者改執行 `/take-this` 參與規劃、先執行 `/grill-me`／`/grill-with-docs`／`/grill-them`
釐清，或對大型未決任務執行 `/wayfinder`。取得明確放行後繼續；全綠則直接前進。

完成判準：已記錄 tracker 設定、唯一任務與 grilling 來源；run ledger 已接手或已
建立；三項風險各有紅綠結論；若有紅燈，已有使用者明確放行紀錄，且提案是從全開起跳。

## 2. 完成開局（已有 tickets 時跳過）

開局整段交給一個**開局 agent**。以本 skill 的 base directory 解析出同層
`../take-this/SKILL.md` 與 `ASKING.md` 的絕對路徑，連同 ledger 路徑交給它，要它全文讀取後
照做 `take-this` 的完整步驟。步驟 1 若已接棒 grilling 成果，先把成果的落點（路徑或 URL）
與本 session 已定的決策寫進 ledger 第 2 欄，開局 agent 從那裡接需求脈絡，不靠主持人轉述。
它依上下文預算回報 spec 識別、附阻塞邊的票列表、frontier 與 run 層代答清單，spec 與票的
全文留在 tracker。

一個 run 只開一次開局 agent。它中斷或回報不完整時，從 ledger 的下一個動作續開一個，
不重跑已發布的部分。

開局 agent 交付之後、進入步驟 3 之前，執行 `ASKING.md` 第 4 節的**唯一裁決點**。

完成判準：tickets 已發布到已設定的 tracker，且每個阻塞邊都已明載；開局 agent 的需求脈絡
指向步驟 1 選定的同一份 grilling 成果；裁決點恰好執行一次。

## 3. 清票

以本 skill 的 base directory 為起點，讀同層的 `../get-to-work/SKILL.md` 並照做：把步驟 2
建立的 tickets，或步驟 1 找到的可執行環，以 tracker 原生識別（GitHub issue 編號／URL，或
Local Markdown 路徑）作為它的明確引數，沿用本 run 的 ledger。期間中途事項只走
`ASKING.md` 第 4 節的三條出路。

完成判準：`get-to-work` 已停止；交付給它的每張票都出現在對帳表中，且明列已交付、卡住
或待裁決結果及其證據；期間沒有任何提問。

## 4. 交棒

最終報告是 ledger 的收束，每個發現**只有一處正本**：寫在它該在的地方一次，其他段落只引用
識別碼與路徑，也不內嵌 diff、測試日誌或 agent 報告。逐項列出：

- 任務範圍、採用的 grilling 來源，以及三項風險判定。
- **需授權動作的結果**（ledger 第 5 欄）：每個送出的動作與放行結果，擋下的附權限規則片段。
- **run 層自答清單**，沒有自答時明記「無」；票級代答只給位置。接著做 `ASKING.md` 第 4 節
  的**複核**。
- **人工作業清單**：每項都要有照著就能做完的步驟。步驟多或要走第三方介面時，呼叫
  Skill tool 帶入 `wizard` 產生互動式 wizard，並在清單裡指向它。
- 每條線的交付（GitHub 總 PR，或 Local Markdown 整合分支與 tip SHA）與**對帳表**。
- 期間開票產生的 raw tickets、請使用者執行 `/triage` 的建議，以及所有待裁決項目。
- **本輪計量與預算**（ledger 第 9 欄）：上限與用量；run 因上限或無進展斷路停下時，寫出停在哪一項與卡在哪裡。

報告送出後，步驟 5 不執行時，把 ledger 第一行改成 `<!-- sorry-matt:run ended -->`。

完成判準：七類資訊齊備；需授權動作的結果與實際送出的動作逐項對得上；每條線都有可追溯的交付物
與驗收證據，足以讓未參與過程的人決定是否合併總 PR 或本地整合分支；人工作業清單的每一項
都有可照做的步驟或對應的 wizard；報告裡沒有任何一段是別處原文的複本；步驟 5 不執行時，ledger
第一行已是 ended 標記。

## 5. 目視驗收（條件性）

只有在某張票的驗收項無法以機械方式驗證時才執行，位置固定在步驟 4 之後 —— 交棒報告先出，
使用者才知道每一項要拿什麼來對。一次一項，附操作步驟與可直接開啟的 URL 或視窗，取得回應
再進下一項。它是驗收程序而非裁決，所以不受「只有一個裁決點」限制。

逐項結果回填對帳表。驗收不通過的票依 `get-to-work` 的規則標為卡住，不在這裡改碼。最後一項
回填後，把 ledger 第一行改成 `<!-- sorry-matt:run ended -->`。

完成判準：每個無法機械驗證的驗收項都有使用者的逐項回應與落點，或已明記不適用；ledger 第一行
已是 ended 標記。
