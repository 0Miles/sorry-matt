# Build the UI right：先查、補齊狀態、再交給眼睛

開工先全文讀取同目錄的 [FRONTEND.md](FRONTEND.md)。它是**前端契約**：來源的仲裁順序、
**狀態矩陣**、無障礙底線、證據三級與瀏覽器支援政策都以它為準，本檔只寫順序。

這次要新增頁面、元件、表單或流程，或要改動既有介面的結構與資訊層級，而對話中還沒有
**介面定案**時，先呼叫 Skill tool 帶入 `figure-out-the-ui`，拿到定案再往下。

## 1. 認清專案

讀專案指示檔與這次改動周邊的程式碼，找出框架、design tokens、字型、密度、主題、元件庫與
瀏覽器支援政策。再找出與這次改動最接近的既有元件：新程式碼沿用它的 tokens、命名、結構與
樣式寫法。

完成判準：這次要沿用的每個 token 與元件都指得出檔案位置；專案裡找不到對應物、必須新造的
項目已逐項列出。

## 2. 先查再寫

這次用到的每個 UI 機制 —— 對話框、彈出層、表單驗證、表格、版面、主題、動效、捲動 ——
在動手前各查一次，依契約第 1 節的分工：做什麼與為什麼問 `master-design`，用哪個平台 API
與要不要 fallback 問 `modern-web-guidance`。查到的指引與專案既有寫法衝突時，專案勝。

完成判準：每個用到的 UI 機制都對得上一份查過的指引，或已記為「指引未涵蓋」。

## 3. 補齊狀態矩陣

對每個受影響的畫面或元件，把契約第 2 節的**狀態矩陣**逐格填成「已實作」或「不適用」。
實作時守住契約第 3 節的無障礙底線與第 5 節的瀏覽器支援政策。

完成判準：矩陣沒有空格；每個「已實作」都指得出程式碼位置；每個「不適用」都有原因。

## 4. 交給眼睛

呼叫 Skill tool 帶入 `actually-look-at-the-ui`，把狀態矩陣與這次的驗收項交給它當要看的主張。
它回報的失敗項修到通過；修法動到別的狀態時，那幾格重看。

回報四件事：沿用了哪些既有 tokens 與元件、狀態矩陣、查過的指引、`actually-look-at-the-ui`
的證據表。

完成判準：每個主張都有 `actually-look-at-the-ui` 給的結果；每個失敗項都已修到通過，或原樣
寫進回報。
