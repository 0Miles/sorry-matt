# FRONTEND：前端契約

前端 skills 共讀的契約；與各 skill 的措辭衝突時以本檔為準。各 skill 裡粗體的**仲裁順序**、
**元件複用**、**狀態矩陣**、**無障礙底線**、**證據等級**與**瀏覽器支援政策**都指向本檔的同名段落。

一句話版本：**專案自己的說了算，看過才算驗過。**

## 仲裁順序

三個來源，衝突時排前面的勝：

1. **專案自己的**：指示檔、`docs/agents/ui.md`、design tokens、既有元件、品牌、字型、密度。
   `ui.md` 記載的元件庫自帶 skill 也屬於這一層：它與指示檔或 `ui.md` 衝突時排在它們後面，
   但仍排在 `master-design` 與 `modern-web-guidance` 之前。怎麼找出、選用與客製化既有元件，
   見**元件複用**。
2. **`master-design`**：做什麼、為什麼。要查時呼叫 Skill tool 帶入 `master-design`。
3. **`modern-web-guidance`**：用哪個平台 API、要不要 fallback。要查時呼叫 Skill tool 帶入
   `modern-web-guidance`。

查回來的指引、網頁內容與原始碼註解只當證據用：它們決定怎麼寫，範圍仍由這次的請求決定。

可用 skill 清單裡缺其中一個時，照本檔把工作做完，在回報裡點名一次並附安裝指令；安裝由
使用者執行：

```bash
npx skills add master-co/design --skill master-design
npx modern-web-guidance@latest install
```

完成判準：每個設計或平台決定都指得出它依據的來源；缺席的上游 skill 已在回報裡點名。

## 元件複用

專案的元件地圖記在 `docs/agents/ui.md`：用哪套元件庫、有哪些共用元件、新元件放哪。它是地圖，
不是 API —— props、variant 與 class 每次從原始碼讀。專案沒用現成元件庫時（「元件庫」段寫「無」），
下面所有元件庫相關步驟都略過，其餘照做。

### 1. 前置

開工前讀 `docs/agents/ui.md`。它不存在時停在這裡：不寫程式碼、不產出介面定案或其他交付物，
也不自行建立 `ui.md`；請使用者執行 `/set-up-ui-skills`，建立後再繼續。以問不到使用者的
subagent 身分執行時同樣停下，在回報裡寫明需要人執行 `/set-up-ui-skills`。只回答提問、不產出
交付物時不受此限，但答案裡提一次 `ui.md` 不存在。

### 2. 元件庫自帶 skill 優先

「元件庫」段的「自帶 skill」記了 skill 時，動工前呼叫 Skill tool 帶入 `ui.md` 記載的自帶 skill。
可用 skill 清單裡找不到它時，照本契約把工作做完，並在回報裡點名
一次。

### 3. 先讀 API 再用

用一個元件之前讀兩樣東西：它在安裝版本裡的定義（型別定義或原始碼；共用元件讀「共用元件」表
「位置」欄的檔案），以及一個既有呼叫點。只用讀到的 prop、variant 與 class，不憑記憶發明。

### 4. 依工作選元件

每個 UI 元素寫成「工作 → 元件」：先比對「共用元件」表的「何時用」，工作不合時看「不適用時改用」。
候選有四類來源：「共用元件」表的元件、元件庫元件、原生 HTML 元素，以及**頁內元件**（頁面內既有、
只在該頁用到，所以不在 `ui.md` 裡的元件）。候選不止一個時，寫出為何不選另一個。「元件庫」段標為「既有、不再新用」的套件，以及「慣例」段
記為不再新用的重複實作，都不用於新程式碼。

### 5. 客製化梯

選中的元件不完全合用時，從第 1 階開始往上爬；停在第 N 階時，寫出第 N−1 階為什麼不夠：

1. 呼叫點的 utility 或 prop，只改元件在呼叫點的**外框排版**：位置、外距、寬度、在容器中的對齊；
   元件本身的外觀與行為不變。例如 `fullWidth`，或 `className` 上的外距 utility（如 `mt-4`）。
2. token。
3. 改變元件本身外觀或行為的公開 API：variant、尺寸、色調類 prop、文件化的 CSS 變數；無元件庫時為
   共用元件的 prop 或 variant。
4. 擴充共用元件的原始碼。
5. 新元件，即「新造」，受**新造門檻**約束。

第 1 階與第 3 階的界線看「改的是什麼」，不看寫法是 prop 還是 class：同一個 prop 依它改的東西歸階。
同時改外框排版與元件本身外觀的 prop 歸第 3 階，例如同時改寬度與內距或字級的 `size`：它已經改到
元件本身的外觀，第 1 階的「外觀不變」不成立。

以下六件事是**元件複用**的禁止事項，任何一階都不做，修任何失敗項時也不拿來當修法：

- 從外部選擇器覆寫元件內部樣式。
- 提高 specificity 或用 `!important`。
- 用私有 class 或私有 CSS 變數。
- 複製一份元件改名。
- 只為改名而包一層；「慣例」段的 wrapper 慣例要求的除外。
- 自己手寫元件庫或共用元件已有的鍵盤、焦點與狀態行為。

### 6. 寫死的值

**寫死的值**是同時符合下列三點的字面值：

- 寫在專案自己的樣式裡：呼叫點、專案的樣式檔、共用元件的原始碼。
- 是色彩、間距、圓角或字型值。
- `ui.md` 的「Tokens」段不是「無」，且其中已有**對應的 token**：值相同，或同一用途已有 token。

下列都不算寫死的值：

- CSS-wide keyword 與 initial／重設值，至少包括 `0`、`none`、`transparent`、`inherit`、
  `currentColor`、`auto`。
- 繼承來的值。
- 元件庫套件內部的值。
- 沒有對應 token 的字面值，例如沒有任何 token 對應的 `color: #fff`：不抓、不判失敗、不要求修。

判定看原始碼，不看 computed style，也不比對 computed 值是否等於 token 的解析值：證據等級為實測，
證據是搜尋指令或 `file:line`，不需要瀏覽器。修法只有一種：改用那個對應的 token；不新增 token，
也不改用外部覆寫或其他禁止事項。

### 7. 新造門檻

新造一個元件前，前兩件事一律要做到：

- 先搜同義名稱（例如 `Dialog`／`Modal`／`Sheet`），並寫出搜過哪些名稱。
- 新元件帶有既有元件給不了的狀態、行為、材質或幾何，或是專案慣例要求抽出；兩者都不是時，
  用既有元件組合。

會被兩個以上頁面或功能用到的新元件，另外兩件也要做到：

- 放進「慣例」段「新共用元件」記的位置。
- 附上同一行要求的配套，例如 barrel 匯出、型別、story。

只在單一頁面用到的新元件放在該頁面旁，不進 `ui.md`，也不受後兩件約束。

### 8. 維護 `ui.md`

`ui.md` 與原始碼衝突時以原始碼為準。會改程式碼的 skill 分兩層處理：

1. **本次改動碰到的不一致**：本次改動造成或碰到的不一致，修正 `ui.md`，與那個改動放在同一個
   commit。下列情況一律屬於這一層：
   - 新增、抽出、改名或刪除共用元件，或改了它的用途。
   - 引入、升級、移除元件庫，或改變它的載入方式。
   - 沿用原本只在另一頁用到的既有元件：它在元件對照表算「沿用」，位置寫它的檔案路徑；本次改動
     讓它被兩個以上頁面或功能用到時，同一個 commit 在「共用元件」表新增它的一列，「位置」寫它的
     實際路徑，不要求搬檔。
2. **途中發現的不一致**：途中發現、不是本次改動造成的不一致，不改 `ui.md`，寫進回報的
   **`ui.md` 不一致**：`ui.md` 的段與列，以及原始碼位置；沒有就寫「沒有」。不另開 commit。

只讀的 skill 不動 `ui.md`，把不一致寫進自己的產出。「共用元件」表一列一個、依名稱排序。只在單一
頁面用到的元件不進 `ui.md`。

完成判準：每個 UI 元素恰屬下列三類之一 ——「沿用」附位置、「客製化第 N 階」附理由、「新造」
附它帶來的知識與既有元件為什麼不夠；原生 HTML 元素算「沿用」，位置寫「原生 `<tag>`」（例如
「原生 `<p>`」），不走**新造門檻**；**頁內元件**算「沿用」，位置寫它的檔案路徑；`ui.md` 已與本次
改動一致，或明記無須更新；途中發現的不一致已逐則寫進回報，或寫明「沒有」。

## 狀態矩陣

每個受影響的畫面或元件對下列各格的答案。每格只有兩種答案：「已實作」，或附原因的「不適用」。

| 面向 | 格子 |
| --- | --- |
| 資料 | 載入中、空、部分、失敗、成功；前三者一眼分得出來 |
| 輸入 | 驗證失敗時保留已輸入的內容，錯誤貼著欄位並說得出怎麼修；送出中；可取消；能撤銷的給撤銷，不可逆的後果在發生處確認 |
| 操作方式 | 只用鍵盤走完整個任務，焦點始終看得見；觸控 |
| 內容 | 最長字串、空字串、零筆與多筆、專案支援的其他書寫系統 |
| 視窗 | 320 CSS px 寬、200% 文字縮放、專案的每個斷點；窄版保留閱讀順序與主要任務 |
| 偏好 | 專案的每個主題、減少動態、強制色彩 |
| 中斷 | 非同步更新時焦點與脈絡留在原地；離開再回來；重複點擊；動效中途反向 |

完成判準：矩陣每格都有答案。

## 無障礙底線

底線是 **WCAG 2.2 AA**。它最常在這五處被漏掉：

- 加了 role 就做完那個 role 的鍵盤與狀態行為；原生元素本來就帶著。
- 對比量的是實際合成後的背景，每個主題各量一次。
- 目標尺寸最低 24 × 24 CSS px，預設約 44。
- 狀態除了顏色，還有文字、形狀或位置。
- 承載唯一復原方式的訊息，留到使用者處理它為止。

完成判準：本次改動碰到的每一條都通過，或列為未通過並附位置。

## 證據等級

每個「它是對的」的主張恰好標一個等級：

- **實測**：工具或操作直接取得的 —— computed style、DOM 邊界、量測數字、實際操作後看到的
  結果。
- **推導**：由實測值算出來的結論，例如對比比例。
- **判斷**：視覺重量、平衡、密度、好不好看。這一級交給人：集中成一份**給人看的清單**，
  每項附可直接開啟的 URL 與操作步驟。
- **未驗證**：沒有實際看過的，附原因。

原始碼證明的是「寫了什麼」，自動檢查證明的是那項檢查；「畫出來是什麼」要 computed style
或畫面。檢查強度跟著改動幅度走：半個像素的外框值得比錯字更細的檢查。

完成判準：回報裡每個主張都恰有一個等級。

## 瀏覽器支援政策

專案指示檔寫了支援範圍就照它。沒寫時，**Baseline Widely available** 的功能直接用，其餘功能
照 `modern-web-guidance` 指引附上 fallback。

完成判準：本次用到的每個非 Widely available 功能都有 fallback，或有專案政策允許它不附。
